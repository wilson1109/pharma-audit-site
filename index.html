交给一套可复核的流程

上传一份被审文件和一套基准（制度、规程），系统逐条比对后给出问题清单和完整性结论。 每条问题都附依据原文。判断留给人，系统只负责把该看的地方找出来。

定位

辅助人做初审，不替代人的判断

它输出的是待复核的问题候选。定位、依据、原文都摆在明面上，最后那一票由人投。

先过一遍

把可能有问题的位置标出来，人只看这几页，不必从头通读。

每条都有出处

写清基准第几条、被审件怎么写的、两者差在哪，原文直接贴出来。

判断留给人

确认或误报由人裁决并落库，裁决结果会变成下一次审核的参考。

诚实边界

不承诺准确率。未纳入审核范围的要求、失败或部分完成的专家，都单独列成清单，不混进「没问题」里。规格里标 ?? 的数是尚未标定的，不填估计值。

审核流程

从入库到报告，六步

前两步定口径，中间三步出候选问题，最后一步把结论写成能归档的文档。

  1. 1

    基准入库

    制度、规程进知识库，切成条款，按章节和编号建索引，作为比对依据。

  2. 2

    上传被审件

    Word 走结构化抽取；PDF 走异步解析，版面、表格、图、公式分开处理，失败就报错，不静默降级。

  3. 3

    解析与脱敏

    抽出条款结构；敏感信息换成映射标记，映射可以人工改，改完按新映射重写产物。

  4. 4

    专家并行审核

    五个域专家各管一段，知识评审按需开到 8 个实例，每个槽位挂一个技能。

  5. 5

    逐条复核

    确认的进经验库，驳回的留痕，下次同类问题少报一次。存在分歧的条目保留 [存在未决分歧] 标记。

  6. 6

    出报告

    按四档处置级分组，附文件画像、未锚定发现、未就绪专家清单，可导出 Word。

核心能力

让人能复核的六个设计

每一处对应一个具体问题：专家不够细、技能塞不下、结论说不清、数据不敢传。

五域专家 + 知识评审

数值校准、适用范围、漏项、引用、文件形式五域必派；知识评审按需开到 8 个实例，各盯不同侧面。

必派五域实例可扩

一槽一技能

每个评审槽最多挂一个技能。要同时按多个技能核查就多开实例，责任边界不会糊在一起。

技能路由槽位隔离

逐条依据原文

问题绑定基准条款与原文引用，报告里能对照；找不到基准对应的，单独进「未锚定」清单。

原文引用条款锚点

完整性结论可解释

结论分完成 / 部分完成 / 未完成，并列出失败与部分完成的专家。差在哪，报告里看得见。

三态结论未就绪清单

上传即脱敏

敏感信息在出网前换成映射标记，映射可人工校对；PDF 解析产物按改动后的映射重写。

映射可编辑产物重写

定时无人值守

计划页设好时间与目标，到点自动起审；任务按先来先审排队，停机后按宽限期补跑或记为错过。

计划调度排队可见

复核一次，下一次更准

每次复核都会沉淀：确认的、驳回的、人工补的备注，提炼成可检索的经验条目，下次审核时按相似度召回并注入上下文。经验可以人工改、可以删，也能整库重嵌。总开关在设置页，默认关闭——关了就不提炼、不召回、不注入。

复核裁决人确认或驳回，附理由
提炼条目原文片段 + 要求字段 + 备注
嵌入入库与前语料同库，可增可改
召回注入下次审核按相似度带回

口径与已知限制

审核次数口径：两库的 run 编号有 8 个重叠（运行库 id 50–70 与归档库同号），不能把两库条数直接相加；上表的 106 是把现存记录与回收站里删除的历史 run 合并后按编号去重得到的，编号 1–106 连续。误报率口径：专家槽位开启思考模式后，单文件小样本误报率在 5% 以下；不开启思考模式时误报率会显著升高——上表那组 20.8% 就是未开启阶段的读数，不能与开启后的数放在一起比较。完整性：运行库现存 31 次审核中判为完整 26 次、不完整 3 次、未判定 2 次（两次失败）。自动化测试参数化展开后 7,009 个用例，复跑 6,866 passed / 1 failed / 3 skipped。发现条数不是质量指标——调高推理深度时条数会下降，相似问题被合并了。样本小于 25 个埋点的对照，统计意义不足。

技术架构

四层，一条链路

单体部署、单 worker 运行，不引入额外中间件，换的是可预期和可运维。

接入层

FastAPI 七页界面 + SSE 实时事件流 · 单进程部署

编排层

LangGraph 图编排：分诊 → 多专家并行 → 汇总 → 完整性判定

能力层

混合检索（向量 / 词法 / 融合）· 专家与技能库 · 经验沉淀与召回 · 报告渲染

数据与安全

SQLite（WAL）· AES-256-GCM 密钥库 · 唯一出网口 + 登记过的解析通道

运行形态

Windows + Python 3.12，虚拟环境复用系统包以避免版本漂移。必须单 worker 启动，多 worker 会绕过进程级单轮次门，也会造成 SQLite 写冲突。

数据落地

解析产物、条款结构、图与表索引都留在本机 data/ 下；报告同时产出 Markdown 与 Word，便于归档和二次编辑。

数据与安全

先说清楚数据往哪走

密钥只存密文

AES-256-GCM 加密后入库，密钥由本机机器码派生。换机器就解不开，必须重新录入。这是个取舍：只拿走 data/ 也拿不到密钥。

出网只有一个口

模型与视觉调用统一走单一网关，PDF 解析是登记过的独立通道。两处都有台账，写清发什么、发给谁、什么时候触发。

常见问题

会被问到的几个问题

它能替代审核员吗？

不能，也没这么设计。它输出的是待复核的问题候选：定位、依据、原文都给了，判断仍由人下。报告里每条都留着复核位。

支持哪些文件格式？

Word（.doc / .docx）走结构化抽取；PDF 走异步解析任务，版面、表格、图与公式分开处理，扫描件另做 OCR 复核。解析失败会明确报错，不会静默降级成本地粗解析。

文件内容会不会出网？

会，但边界是明确的：条款文本发往所配置的模型端点，PDF 只发文件字节或页面图像，不发审核问题与报告内容。去向在项目外发台账里逐条登记，需使用方确认后才允许。

使用本系统需要哪些 AI 模型？

三类，都在设置页自己配，不用改代码：
① 聊天模型——审核链路的主力，图片与公式转写也走它（DeepSeek 官方端点已跑通）；
② 嵌入模型——语料与经验的向量化和检索（bge-m3 已跑通）；
③ PDF 解析服务——MinerU 做主解析、PaddleOCR 做扫描件复核，地址由使用方填。
密钥只在本机加密入库，不进配置文件。换供应商只要改配置行。

本系统的实际审核效果受哪些影响？

系统调用的 LLM 模型能力、思考深度会显著影响实际审核效果。同一份被审件只换执行通道与推理深度，命中率就从 87.5% 掉到 75.0% 和 31.3%——模型是这套系统里最大的变量。误报率也一样：专家槽位不开启思考模式时误报率显著升高，开启后降到 5% 以下。

现在是什么状态？

原型阶段，由复星安特金精益运营部开发，七个页面与主链路都可用，功能仍在收敛，规格与缺陷逐条登记。页面上的能力描述以当前实现为准，不承诺准确率数字。
