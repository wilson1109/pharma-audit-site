定位

辅助人做初筛，不替代人的判断

这不是「AI 自动审完出结论」，而是一条把口径固定下来、把证据留住的流水线。

先做初筛

把「可能有问题」的位置标出来，人只需要看该看的那几页，而不是从头通读一遍。

每条都有依据

问题不是「模型说有问题」，而是「基准第 X 条这么写，被审件这么写，两者不一致」，原文一并给出。

判断留给人

逐条「确认 / 误报」由人裁决并落库；存在分歧的条目保留 [存在未决分歧] 标记，不抹平。

诚实边界

不承诺准确率——原型阶段的每一个数都以实测为准，规格里标 ?? 的位置表示「尚未标定」，不填估计值。本次未纳入审核范围的要求、失败或部分完成的专家，都会单独列成清单，不会被静默当成「没问题」。

审核流程

从入库到报告，六步走完

前两步确定口径，中间三步产出候选问题，最后一步把结论写成可归档的文档。

  1. 1

    基准入库

    制度 / 规程进知识库，切成条款级片段，按章节与编号建索引，作为「比对依据」。

  2. 2

    上传被审件

    Word 走结构化抽取；PDF 走异步解析，版面、表格、图与公式分别处理，失败不静默降级。

  3. 3

    解析与脱敏

    抽出条款结构做可读性处理，敏感信息按映射脱敏，映射关系可人工编辑后按新映射重写产物。

  4. 4

    专家并行审核

    五个域专家各司其职，知识评审按需多实例并行；调度给每个槽位指定一个技能。

  5. 5

    逐条复核

    人在问题清单上逐条裁决，确认的进经验库，误报的留痕，用于后续同类判断。

  6. 6

    出报告

    问题按四档严重度分组，附文件画像、未映射发现与未就绪清单，可一键导出 Word。

核心能力

让人能复核的六个设计

每一处都对应一个现实问题：专家不够细、技能塞不下、结论说不清、数据不敢传。

五域专家 + 知识评审

数值校准、适用范围、漏项、引用、文件形式五个域必派；知识评审按需 0–8 个实例，各自盯不同侧面。

必派五域实例可扩

一槽一技能

调度为每个评审槽最多指定一个技能；要同时按多个技能核查，就派多个实例——这样责任边界不会糊在一起。

技能路由槽位隔离

逐条依据原文

每个问题都绑定基准条款与原文引用，报告里能直接对照；没有基准对应的发现单独归入「未映射」。

原文引用条款锚点

完整性结论可解释

结论分「完成 / 部分完成 / 未完成」，并列出失败与部分完成的专家。差在哪，报告里看得见。

三态结论未就绪清单

上传即脱敏

文档中的敏感信息在出网前替换为映射标记，映射可人工校对；PDF 解析产物按编辑后的映射重写。

映射可编辑产物重写

定时无人值守

计划页预设时间与目标，到点自动起审；多任务按先来先审排队，服务停机后按宽限期补跑或记为错过。

计划调度排队可见

技术架构

四层，一条链路

单体部署、单 worker 运行，不引入额外中间件；换取的是可预期和可运维。

接入层

FastAPI 七页界面 + SSE 实时事件流 · 单进程部署

编排层

LangGraph 图编排：分诊 → 多专家并行 → 汇总 → 完整性判定

能力层

混合检索（向量 / 词法 / 融合）· 专家与技能库 · 经验记忆 · 报告渲染

数据与安全

SQLite（WAL）· AES-256-GCM 密钥库 · 唯一出网口 + 登记过的解析通道

运行形态

Windows + Python 3.12，虚拟环境复用系统包以避免版本漂移；必须单 worker 启动——多 worker 会绕过单轮次门，并造成 SQLite 写冲突。

数据落地

解析产物、条款结构、图与表索引都留在本机 data/ 下；报告同时产出 Markdown 与 Word，便于归档与二次编辑。

数据与安全

先说清楚数据往哪走

制药文件不适合「先跑起来再说」。这三条是设计时就定死的，不是事后补的。

密钥只存密文

AES-256-GCM 加密后入库，密钥由本机机器码派生。换机器就解不开，必须重新录入——这是取舍：只拿走 data/ 也拿不到密钥。

出网只有一个口

模型与视觉调用统一走单一网关，PDF 解析是登记过的独立通道。两处都有台账，写了发什么、发给谁、什么时候触发。

数据不整目录外发

data/ 内含企业文件副本与密钥密文，不进仓库、不打包外发；本页也不含任何企业文件内容。

常见问题

会被问到的几个问题

它能替代审核员吗？

不能，也没这么设计。它输出的是「待复核的问题候选」：定位、依据、原文都给了，判断仍然由人下。报告里每条都留有复核位。

支持哪些文件格式？

Word（.doc / .docx）走结构化抽取；PDF 走异步解析任务，版面、表格、图与公式分别处理，扫描件另做 OCR 复核。解析失败会明确报错，不会静默降级成本地粗解析。

文件内容会不会出网？

会，但边界是明确的：条款文本发往所配置的模型端点，PDF 只发文件字节或页面图像，不发送审核问题与报告内容。全部去向在项目 README 的外发台账里逐条登记，且需使用方书面确认后才允许。

为什么必须单 worker、常驻运行？

单 worker 是为了保证「一次只跑一轮审核」的进程级门不被绕过，同时避免 SQLite 写冲突；常驻是为了定时计划能到点触发——服务不在跑，计划不会执行。

现在是什么状态？

原型 / 内部验证阶段。七个页面与主链路可用，功能仍在收敛，规格与缺陷逐条登记。页面上的能力描述以当前实现为准，不承诺准确率数字。
